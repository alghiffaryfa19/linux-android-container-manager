Ya, dari log ini DMA-BUF dari Android sudah berhasil diterima. Masalah sekarang lebih spesifik: EVDI device 0 gagal dibuka, kemungkinan besar module lindroid-drm-evdi belum loaded atau device /dev/dri/card*/EVDI node yang diharapkan belum muncul.

Dan command terakhir memang salah sintaks: lsmod tidak menerima nama module sebagai argumen.

Coba jalankan ini:

Bash
lsmod | grep -E 'lindroid|evdi|drm'

Lalu:

Bash
ls -lah /sys/class/drm/
ls -lah /dev/dri/

Dan cek module:

Bash
modinfo lindroid-drm-evdi

Kalau modinfo tidak menemukan:

modinfo: ERROR: Module lindroid-drm-evdi not found

cari file .ko:

Bash
find /lib/modules/$(uname -r) -type f \( -name '*evdi*.ko*' -o -name '*lindroid*.ko*' \) -print

Kalau ketemu misalnya:

/lib/modules/.../lindroid-drm-evdi.ko

load:

Bash
modprobe lindroid-drm-evdi

atau kalau modprobe tidak bisa menemukan module:

Bash
insmod /path/ke/lindroid-drm-evdi.ko

Kemudian:

Bash
lsmod | grep -E 'lindroid|evdi'
dmesg | tail -100
ls -lah /dev/dri/
ls -lah /sys/class/drm/

Jadi jangan fokus ke DMA-BUF dulu. Sekarang kita perlu melihat apa yang dimaksud EVDI device 0 oleh libevdi dan apakah kernel module memang membuat EVDI DRM device.

Jalankan satu blok ini dan kirim outputnya:

Bash
echo '=== MODULE ==='
uname -r
lsmod | grep -E 'lindroid|evdi|drm'

modinfo lindroid-drm-evdi 2>&1 | head -50

echo '=== MODULE FILES ==='
find /lib/modules/$(uname -r) -type f \( -name '*evdi*.ko*' -o -name '*lindroid*.ko*' \) -print

echo '=== DRM NODES ==='
ls -lah /dev/dri/

echo '=== DRM SYSFS ==='
ls -lah /sys/class/drm/

echo '=== DRM DEVICES ==='
for x in /sys/class/drm/card*/device; do
    echo "--- $x"
    readlink -f "$x"
done

echo '=== KERNEL LOG ==='
dmesg | grep -iE 'evdi|lindroid|drm|dma.?buf' | tail -100

ChatGPT said:

Nah, ini sangat mungkin akar masalahnya.

C
evdi_handle evdi = evdi_open(0);

Pada fork libevdi yang kamu pakai, evdi_open(int device) secara langsung menggunakan:

/dev/dri/card%d

Jadi:

C
evdi_open(0)

berarti membuka:

/dev/dri/card0

Padahal dari hasil pengecekan kita:

card0 = Qualcomm/MSM DRM → physical display
card1 = evdi-lindroid → EVDI

Jadi bridge sedang meminta card0, bukan card1.

Ubah menjadi

Di evdi_bridge.c:

C
evdi_handle evdi = evdi_open(1);

Lalu rebuild:

Bash
cd /usr/src/evdi_bridge

gcc evdi_bridge.c \
    -o /usr/bin/evdi_bridge \
    -ldrm \
    -levdi \
    -L/usr/local/lib \
    -I/usr/local/include

chmod +x /usr/bin/evdi_bridge

Pastikan binary benar-benar memakai lib custom:

Bash
ldd /usr/bin/evdi_bridge | grep libevdi

Harus muncul kira-kira:

libevdi.so.1 => /usr/local/lib/libevdi.so.1

Kemudian:

Bash
systemctl restart evdi-bridge
journalctl -u evdi-bridge -f

Tapi sebelum rebuild, kita bisa membuktikan 100%

Karena card1 memang EVDI, jalankan test kecil:

Bash
cat >/tmp/test-evdi.c <<'EOF'
#include <stdio.h>
#include "evdi_lib.h"

int main(void)
{
    for (int i = 0; i < 2; i++) {
        printf("=== evdi_open(%d) ===\n", i);

        evdi_handle h = evdi_open(i);

        if (h) {
            printf("SUCCESS: card%d\n", i);
            evdi_close(h);
        } else {
            printf("FAILED: card%d\n", i);
        }
    }

    return 0;
}
EOF

gcc /tmp/test-evdi.c \
    -o /tmp/test-evdi \
    -I/tmp/evdi-src/library \
    -L/usr/local/lib \
    -Wl,-rpath,/usr/local/lib \
    -levdi

/tmp/test-evdi

Saya memprediksi hasilnya akan seperti:

=== evdi_open(0) ===
FAILED: card0

=== evdi_open(1) ===
SUCCESS: card1

Kalau benar begitu, diagnosisnya sudah sangat kuat: bridge hardcode evdi_open(0) sementara EVDI Lindroid berada di DRM card1.

Ada satu hal penting lagi

Jangan langsung menganggap semua penggunaan angka 0 harus diganti. Cari dulu seluruh pemanggilan EVDI:

Bash
grep -nE 'evdi_open|evdi_check_device|evdi_open_attached' \
    /usr/src/evdi_bridge/evdi_bridge.c

Dan:

Bash
grep -n -A20 -B10 'evdi_open' /usr/src/evdi_bridge/evdi_bridge.c

Kirim hasilnya. Dari situ kita bisa tentukan apakah cukup:

C
evdi_open(0)

→

C
evdi_open(1)

atau sebaiknya dibuat dynamic detection supaya bridge tidak bergantung pada nomor card1.
